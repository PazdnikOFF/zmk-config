# sweep_dongle

Донгл для Ferris Sweep: `nice!nano v2` + WeAct Studio 1.54″ e-paper
(SSD1681, 200×200). Показатели мака принимает двумя каналами — по USB CDC-ACM,
пока есть кабель, и по своей GATT-характеристике, когда живёт от батареи.

## Зачем

Донгл — **central** сплита. Обе половины стали периферией и приклеены к нему
намертво; переключение между устройствами есть только у донгла.

```
[левая половина]  ──BLE split──┐
                               ├──> [донгл: экран] ──BLE HID──> мак / айпад / ...
[правая половина] ──BLE split──┘
                                      ↑ метрики мака: USB CDC или GATT
```

### Почему связку половинок нельзя разорвать

- У периферии нет ни BLE-профилей, ни поведения `&bt` — раскладка на ней
  вообще не исполняется, переключать ей нечего;
- `CONFIG_BT_MAX_PAIRED=1` в `config/cradio.conf`: у половины ровно один бонд,
  и это донгл. Никто другой к ней не привяжется;
- адреса половин донгл хранит отдельно от хостов, в `peripheral_addrs[]` с
  ключами настроек `ble/peripheral_addresses/N`;
- `&bt BT_CLR_ALL` с третьего слоя безопасен: `zmk_ble_clear_all_bonds()`
  обходит только массив `profiles[]` с хостами и до `peripheral_addrs[]` не
  добирается. Проверено по `src/ble.c`.

Обратная сторона: перепривязать половину к другому донглу можно только через
прошивку `settings_reset`. Это цена формулировки «намертво».

### Переключение хостов

Раскладка исполняется на донгле, поэтому биндинги `&bt BT_SEL n` с третьего
слоя переключают BLE-профили **донгла** — то есть третий слой стал пультом
выбора устройства. Дописывать ничего не потребовалось.

## Выбор выхода: USB или BLE

**Воткнутый кабель уводит нажатия с BLE на USB.** Не «может увести», а уводит
всегда:

```c
/* app/src/endpoints.c */
static enum zmk_transport preferred_transport = ZMK_TRANSPORT_USB;
...
if (is_ble_ready() && is_usb_ready()) return preferred_transport;
```

`preferred_transport` стартует как USB и меняется ТОЛЬКО поведением `&out`,
после чего лежит в настройках (`endpoints/preferred`). Kconfig на выбор выхода
в ZMK нет.

Ловушка в том, что кабель на донгле — это обычно зарядка или снятие логов, а не
намерение печатать по проводу. Со стороны отказ выглядит так: половинки
подключены, донгл виден маку по BLE, экран живой, а текст не набирается. В логе
при этом всё честно:

```
get_selected_transport: Both endpoint transports are ready. Using 0
```

`Using 0` — это USB. Клавиши на слое 2 переключают выход вручную: `&out OUT_USB`
и `&out OUT_BLE`, в правой колонке рядом с управлением BLE.

## Отладочная сборка

`sweep_dongle_debug` из `build.yaml` — та же прошивка со снипетом
`zmk-usb-logging`. Даёт **второй** порт CDC, на который сыплется лог ZMK;
первый остаётся под метрики мака.

```bash
ls /dev/cu.usbmodem*                       # портов будет два
cat /dev/cu.usbmodem<второй> | tee dongle.log
```

Что в нём читать:

| Строка | О чём |
|---|---|
| `le_param_updated: … interval 12 latency 0 timeout 400` | какие параметры соединения назначил хост |
| `reset: … SOFTWARE` / `reset: причин не заявлено` | от чего была предыдущая перезагрузка, см. «Уход в бутлоадер» |
| `link L/R/HOST … rssi=…` | раз в 10 с: параметры и сигнал каждого линка, см. «Одна половинка вязнет» |
| `link R … РАЗРЫВ reason=0x08` | сплит-линк потерян по супервизорному таймауту |
| `keys R … batched=… maxrun=…` | нажатия с одной половинки, пришедшие пачкой — признак застрявшего линка |
| `scan: направленная реклама от …` | половинка с бондом зовёт донгл; нет строки — она молчит, см. «Половинка не цепляется сама» |
| `split_central_connected` / `[SUBSCRIBED]` | половина подключилась к донглу |
| `[DEVICE]: …` | увиденное при скане объявление; **фильтр дубликатов включён**, каждый адрес логируется один раз, так что тишина в логе не означает, что скан не идёт |
| `Trigger key position state change for N` | нажатие доехало с половинки |
| `get_selected_transport` / `Endpoint changed` | куда уходят HID-отчёты |
| `Not sending, no active address for current profile` | активный BLE-профиль пуст, бонда в нём нет |

Проверить встречную сторону — дошло ли до мака — можно счётчиком системы, он
считает нажатия любого источника:

```swift
CGEventSource.counterForEventType(.combinedSessionState, eventType: .keyDown)
```

Пара «в логе отчёт ушёл» плюс «счётчик не сдвинулся» делит задачу пополам:
до этого места виноват донгл, после — мак.

## Параметры соединений: что где задаётся

Три линка, и крутилки к ним лежат в разных местах. Перепутать легко — один
коммит уже был потрачен впустую именно на это.

| Линк | Кто назначает | Где настраивается |
|---|---|---|
| донгл → половинки | донгл (central) | `CONFIG_ZMK_SPLIT_BLE_PREF_*` в `sweep_dongle.conf` |
| донгл → хост | хост | `CONFIG_BT_PERIPHERAL_PREF_*` (PPCP) + `dongle/src/host_params.c` |

**Со стороны половинок сплит не настраивается вообще никак.** Центральный
задаёт параметры прямо в `bt_conn_le_create()`
(`app/src/split/bluetooth/central.c`), а единственный обходной путь —
автоматический L2CAP-запрос Zephyr — ZMK у периферии сплита выключает:

```kconfig
# app/src/split/bluetooth/Kconfig, в ветке if !ZMK_SPLIT_ROLE_CENTRAL
config BT_GAP_AUTO_UPDATE_CONN_PARAMS
    default n
```

Поэтому `CONFIG_BT_PERIPHERAL_PREF_*` в `config/cradio.conf` — мёртвый груз,
сколько бы правдоподобно ни выглядел. Ставить туда что-либо бессмысленно.

Ключевое значение — `CONFIG_ZMK_SPLIT_BLE_PREF_LATENCY`. Дефолт ZMK равен 30, и
при интервале 7.5 мс это до 225 мс, на которые половинка вправе замолчать;
ровно на столько же растягивается окно расхождения нажатий с двух рук по
порядку. У нас стоит 0. Платим за это автономностью половинок (радио
просыпается каждые 7.5 мс), потребление донгла не меняется — центральный
дежурит на каждом событии соединения при любой latency.

## Уход в бутлоадер при подключении кабеля

Бутлоадер Adafruit уходит в UF2 по двойному ресету, то есть «воткнул провод — и
сразу режим прошивки» всегда означает две перезагрузки подряд. Чьи они, снаружи
не видно, и гадать тут дороже, чем измерить.

Собрать `sweep_dongle_debug`, снять лог со второго порта CDC и посмотреть
строку `reset:` на четвёртой секунде после старта:

- `SOFTWARE`, `LOCKUP` или `WATCHDOG` — упала прошивка и перезапустилась сама
  (`CONFIG_RESET_ON_FATAL_ERROR`). Лог падения будет тут же рядом;
- **`причин не заявлено`** — регистр `RESETREAS` обнулился, то есть питание
  пропадало физически. У nRF52 отдельных битов на подачу питания и просадку
  нет, поэтому это одно и то же значение. Ошибки в прошивке здесь нет, смотреть
  надо на питание: панель e-paper запитывается через ключ `EXT_POWER` на P0.13 с
  задержкой 50 мс — ровно тогда, когда хост ещё разбирается с enumeration.
  Порядок проверки: другой кабель → порт с внешним питанием → старт с
  **отключённой панелью**. Если без панели проблема уходит, дело в броске тока;
- `PIN` — кнопка, в том числе штатный двойной ресет.

## Одна половинка со временем начинает вязнуть

Симптом: через какое-то время печати одна половинка отвечает с задержкой, и
буквы с неё встают не на свои места.

**Перестановку даёт протокол сплита, а не сам линк.** Половинка шлёт не
события, а снимок битовой карты всех своих клавиш, и донгл поднимает изменения
из снимка в порядке *номера позиции* (`split_central_notify_func` в
`app/src/split/bluetooth/central.c`). Пока линк успевает, в каждом снимке ровно
одно изменение, и порядок верный. Когда линк встаёт:

1. нотификация на половинке ждёт буфер без таймаута (`bt_att_create_pdu`
   выделяет его с `K_FOREVER`), и очередь отправки стоит;
2. очередь снимков (`CONFIG_ZMK_SPLIT_BLE_PERIPHERAL_POSITION_QUEUE_SIZE`, 10)
   переполняется, через 100 мс ZMK выбрасывает старейший
   (`send_position_state` в `service.c`);
3. следующий доехавший снимок несёт сразу несколько изменений — и они выходят
   по возрастанию номера клавиши. Короткое нажатие, целиком уместившееся в
   выброшенных снимках, пропадает вовсе.

Сверху ложится межручная перестановка из zmk#1633. Лечить поэтому надо затык
линка, а он бывает от двух причин, снаружи неотличимых:

- **Радио.** У дальней от донгла половинки меньше запас по сигналу. Металл,
  расстояние, USB 3 рядом с донглом (документация ZMK называет его прямо, а
  донгл одно время сидел на USB3-хабе).
- **Планирование.** Линк к хосту у донгла периферийный и тикает по часам мака,
  сплит-линки центральные и тикают по часам донгла. Часы расходятся на десятки
  ppm, якорь линка к хосту медленно ползёт по циклу 7.5 мс и через какое-то
  время наезжает на один из сплит-линков — события одного из них начинают
  пропускаться, пока якорь не уползёт дальше. Справка Zephyr к
  `BT_CTLR_SCHED_ADVANCED` описывает ровно это («peripheral roles drifting into
  active central roles»), но в пиненном Zephyr защита не работает: новый LLCP
  не считает смещения для запроса параметров из периферийной роли —
  `ull_cp_conn_update()` получает `offsets = NULL`, а код смещений в
  `cu_prepare_update_ind()` при `SCHED_ADVANCED` выключен. **Линк к хосту не
  рвётся и при выводе через USB**: смена транспорта BLE-соединение не трогает
  (`endpoints.c`), смена профиля тоже (`zmk_ble_prof_select`).

Различить помогает `sweep_dongle_debug` (флаг
`CONFIG_SWEEP_DONGLE_DEBUG_LINKS`). Раз в 10 секунд:

```
link L slot=0 int=7.50ms lat=0 to=4000ms rssi=-58
link R slot=1 int=7.50ms lat=0 to=4000ms rssi=-83
link HOST int=15.00ms lat=0 to=4000ms rssi=-49
keys L slot=0 n=51 batched=0 maxrun=1
keys R slot=1 n=38 batched=14 maxrun=6
```

- `batched` — события одной половинки, пришедшие не дальше 1 мс друг от друга.
  Человек так не печатает (дребезг одной клавиши 5 мс), так выглядит линк,
  который постоял и выплюнул накопленное. Единичные — норма (одновременное
  отпускание), `maxrun` 3 и больше с одной стороны — затык.
- `rssi` у затыкающейся половинки заметно хуже другой (ниже −80) — **радио**:
  переставить донгл ближе к ней, убрать с USB3-хаба, удлинитель.
- `rssi` у обеих нормальный, а пачки растут у одной и потом сами проходят —
  **планирование**.
- `РАЗРЫВ reason=0x08` — линк потерян по супервизорному таймауту, это уже не
  затык, а обрыв.

**A/B без перепрошивки.** Донгл кабелем напрямую в мак (не через хаб), трекпад
тоже кабелем, Bluetooth на маке выключить. Линк к хосту исчезает, в эфире у
донгла остаются только половинки. Если за то же время печати затык не
появляется — дело в планировании; если появляется — в радио.

## Половинка не цепляется сама после перезагрузки донгла

Симптом: донгл перезагрузился (например, от втыкания кабеля), левая половинка
подключилась сама, правую приходится ресетить руками.

Механизм найден по исходникам ZMK v0.3 и Zephyr 3.5, и он связан с
предыдущим разделом:

1. Половинка с бондом рекламирует **только направленно** — на адрес донгла.
2. Для направленной рекламы Zephyr сначала проверяет, нет ли уже объекта
   соединения с этим адресом: `le_adv_start_add_conn()` →
   `bt_conn_exists_le()` → **`-EINVAL`**. Объект в состоянии `DISCONNECTED`,
   на который ещё есть ссылки, считается существующим — это прямо написано в
   комментарии к функции. Поэтому `CONFIG_BT_MAX_CONN=2` не помогает:
   проверка срабатывает раньше выделения нового объекта.
3. Ссылку держит поток нотификаций ZMK: `bt_gatt_notify(NULL, …)` →
   `notify_cb` берёт соединение через `bt_conn_lookup_addr_le()` и не
   отпускает, пока `gatt_notify` ждёт буфер с `K_FOREVER`. То есть ссылка жива
   ровно тогда, когда линк перед разрывом стоял.
4. ZMK перезапускает рекламу из `disconnected()` через системную очередь
   (кооперативный приоритет −1), а поток нотификаций вытесняемый
   (`CONFIG_ZMK_SPLIT_BLE_PERIPHERAL_PRIORITY`, 5). Реклама запускается
   первой, пока ссылка ещё жива, — отказ детерминирован.
5. `advertising_cb` на ошибке только пишет `Failed to start advertising` и
   **больше не пробует**. Повтора нет и в ZMK main (проверено 11.09.2026).

Половинка остаётся в эфире немой до ресета. Левая в момент разрыва стояла без
очереди, её объект соединения освободился сразу — поэтому она и цепляется.

Лечение — `CONFIG_SWEEP_SPLIT_READVERTISE` (по умолчанию включён на
половинках, код в `dongle/src/split_readvertise.c`): пока связи нет, раз в две
секунды запускается та же low-duty-направленная реклама, в которую ZMK
переходит сам. Если реклама уже идёт, Zephyr отвечает `-EALREADY` и ничего не
происходит, так что лишнего расхода нет. **Требует перепрошивки половинок.**

С донгла проверяется отладочной сборкой: после его перезагрузки в логе должна
появиться строка `scan: направленная реклама от <адрес>` от обеих половинок.
Если адреса одной из них нет — молчит она сама, донгл ни при чём.

## Какая плата есть какая

Все три платы — nice!nano v2, и в бутлоадере они неразличимы: том называется
`NICENANO` у любой. Отличать их можно только по серийному номеру USB, он же
уникальный идентификатор чипа и не меняется ни при перепрошивке, ни при входе
в бутлоадер.

| Серийник | Имя на USB | Плата |
|---|---|---|
| `0E45FB20FA090F7A` | `Sweep Dongle` | донгл |
| `84F4C5EE425E77D1` | `Cradio` | левая половина |
| `8A21548861988209` | нет имени | правая половина |

Имя на USB берётся из `CONFIG_ZMK_KEYBOARD_NAME`, а в шилде `cradio` оно
задано только для левой половины — правая его не объявляет, поэтому строки
продукта у неё нет вовсе. Заодно это отличает половины друг от друга без
серийников.

Посмотреть, что подключено:

```bash
ioreg -p IOUSB -w0 -l | grep -E '"USB Product Name"|"USB Serial Number"'
```

**Проверять серийник перед записью обязательно.** Прошивка донгла, залитая в
половину, делает её центральным устройством: она перестаёт подключаться к
донглу и при этом честно представляется как `Sweep Dongle` — то есть проверка
«появилось ли нужное имя после записи» такую ошибку не ловит. Именно так одна
половина и была потеряна на полдня.

## Распиновка

| Сигнал панели | Пин nice!nano | GPIO nRF52840 | Ряд |
|---|---|---|---|
| VCC | `VCC` (3.3 В) | — | правый |
| GND | `GND` | — | правый |
| SCL (SCK) | `D15` | P1.13 | правый |
| SDA (MOSI) | `D14` | P1.11 | правый |
| CS | `D2` | P0.17 | левый |
| D/C | `D3` | P0.20 | левый |
| RES | `D4` | P0.22 | левый |
| BUSY | `D5` | P0.24 | левый |

MISO не подключается — SSD1681 ничего не отдаёт.

Порядок пинов на гребёнке модуля WeAct сверять **по шелкографии**, а не по
позиции: у разных ревизий он отличается.

### Почему не штатный `pro_micro_spi`

Дефолтный `spi1_default` у nice!nano сажает MOSI на **P0.10**, а это NFC-вывод.
`CONFIG_NFCT_PINS_AS_GPIO` в дереве ZMK не включается нигде, поэтому P0.09 (`D10`)
и P0.10 (`D16`) как GPIO недоступны. В оверлее pinctrl переопределён: MOSI
уходит на P1.11, MISO не заявляется.

### Питание

Гребёнка `VCC` у nice!nano v2 запитана через ключ на P0.13 (узел `EXT_POWER`,
`zmk,ext-power-generic`). `CONFIG_ZMK_EXT_POWER` по умолчанию `y`, ключ
включается на старте с задержкой 50 мс — но если внешнее питание когда-нибудь
выключится, дисплей встанет. Глубокий сон на донгле отключён.

## Экран

Рисуется через штатный хук ZMK `zmk_display_status_screen()`
(`CONFIG_ZMK_DISPLAY_STATUS_SCREEN_CUSTOM`), код — в `dongle/src/screen.c`.

Отдельная политика обновления e-paper не понадобилась: `display_tick_cb` в ZMK
— это просто `lv_task_handler()`, а LVGL уходит во flush только по
инвалидации. То есть панель обновляется ровно тогда, когда меняется текст.
Отсюда два требования:

- `CONFIG_LV_Z_VDB_SIZE=100` — полноэкранный буфер (200×200×1 бит = 5000 байт).
  При меньшем LVGL сбрасывает кадр полосами, а `ssd16xx` делает refresh на
  каждый `display_write` — вместо одного обновления вышло бы несколько подряд;
- `set_text_if_changed()` в `screen.c` — `lv_label_set_text` инвалидирует
  область независимо от того, изменился текст или нет.

Весь текст на экране — ASCII: встроенные шрифты Montserrat кириллицы не
содержат.

## Kscan-заглушка

Клавиш нет, но ZMK требует `zmk,kscan`. `zmk,kscan-mock` не подошёл: без
свойства `events` он не компилируется (`DT_N_S_kscan_P_events_LEN`), а задержка
события в нём кодируется 15 битами — отложить дольше 32.7 с нельзя. Поэтому
обычный `zmk,kscan-gpio-direct` на один физически не разведённый вывод `D9`.

## Протокол от агента на маке

Строки, ключи в произвольном порядке, незнакомые игнорируются, отсутствующие
сохраняют прежнее значение:

```
layout=RU cpu=23 mem=61 disk=142 batt=87 chg=1
```

Разбор общий для обоих каналов (`dongle/src/host_proto.c`). Раз в 5 секунд —
чаще e-paper всё равно не перерисуется. Сервис `f1ef61b7-…`, характеристика
`a336bc14-…`, запись требует шифрования, то есть сопряжения.

## Темпы обновления экрана

Блоки обновляются раздельно, и это принципиально. `ssd16xx` пишет только во всю
ширину, поэтому Zephyr расширяет любую грязную область до полной ширины
(`lvgl_rounder_cb_mono`, `SCREEN_INFO_X_ALIGNMENT_WIDTH`) — обновляется
горизонтальная полоса. Отрисовка далёких блоков в одном проходе склеилась бы в
полосу почти во весь экран.

| Блок | Когда |
|---|---|
| Заряд трёх устройств | не чаще раза в 5 с |
| Ресурсы мака | поводом не являются вовсе, рисуются попутно со сдвигом 1.5 с |
| BT-профиль | не чаще раза в 2 с |
| Слой | после 5 с стабильности |

Отрисовка вынесена в отдельную очередь работ
(`CONFIG_ZMK_DISPLAY_WORK_QUEUE_DEDICATED`). По умолчанию ZMK крутит её в
системной очереди — той же, через которую идут события клавиш от половинок, — а
`ssd16xx` на каждом обновлении ждёт на пине BUSY сотни миллисекунд. Ввод из-за
этого вставал колом.

## Энергосбережение

Пять минут без нажатий — панель не трогается совсем. Глубокий сон намеренно
выключен: он гасит радио, а разбудить донгл нажатием на половинке можно только
по радио, своих кнопок у него нет.


## Сборка

Только через GitHub Actions: пуш в репозиторий запускает
`build-user-config@v0.3`, готовые `.uf2` лежат в артефактах сборки.

```bash
gh run download --name firmware
```

Локальная сборка в контейнере была, но от неё отказались: воркспейс west это
79 тысяч файлов на 2.2 ГБ, и в индексируемом Spotlight каталоге он вгоняет
macOS в многочасовую переиндексацию — до отъедания свопа и подтормаживания
ввода. Если понадобится вернуть, разворачивать воркспейс надо **вне**
`~/Documents`.
