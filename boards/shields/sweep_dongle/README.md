# sweep_dongle

Донгл для Ferris Sweep: `nice!nano v2` + WeAct Studio 1.54″ e-paper
(SSD1681, 200×200). Показатели мака принимает двумя каналами — по USB CDC-ACM,
пока есть кабель, и по своей GATT-характеристике, когда живёт от батареи.

## Зачем

Донгл — **central** сплита. Обе половины стали периферией и приклеены к нему
намертво; переключение между устройствами есть только у донгла.

```
[левая половина]  ──BLE split──┐
                               ├──> [донгл: экран] ──BLE HID──> мак / айпад / ...
[правая половина] ──BLE split──┘
                                      ↑ метрики мака: USB CDC или GATT
```

### Почему связку половинок нельзя разорвать

- У периферии нет ни BLE-профилей, ни поведения `&bt` — раскладка на ней
  вообще не исполняется, переключать ей нечего;
- `CONFIG_BT_MAX_PAIRED=1` в `config/cradio.conf`: у половины ровно один бонд,
  и это донгл. Никто другой к ней не привяжется;
- адреса половин донгл хранит отдельно от хостов, в `peripheral_addrs[]` с
  ключами настроек `ble/peripheral_addresses/N`;
- `&bt BT_CLR_ALL` с третьего слоя безопасен: `zmk_ble_clear_all_bonds()`
  обходит только массив `profiles[]` с хостами и до `peripheral_addrs[]` не
  добирается. Проверено по `src/ble.c`.

Обратная сторона: перепривязать половину к другому донглу можно только через
прошивку `settings_reset`. Это цена формулировки «намертво».

### Переключение хостов

Раскладка исполняется на донгле, поэтому биндинги `&bt BT_SEL n` с третьего
слоя переключают BLE-профили **донгла** — то есть третий слой стал пультом
выбора устройства. Дописывать ничего не потребовалось.

## Выбор выхода: USB или BLE

**Воткнутый кабель уводит нажатия с BLE на USB.** Не «может увести», а уводит
всегда:

```c
/* app/src/endpoints.c */
static enum zmk_transport preferred_transport = ZMK_TRANSPORT_USB;
...
if (is_ble_ready() && is_usb_ready()) return preferred_transport;
```

`preferred_transport` стартует как USB и меняется ТОЛЬКО поведением `&out`,
после чего лежит в настройках (`endpoints/preferred`). Kconfig на выбор выхода
в ZMK нет.

Ловушка в том, что кабель на донгле — это обычно зарядка или снятие логов, а не
намерение печатать по проводу. Со стороны отказ выглядит так: половинки
подключены, донгл виден маку по BLE, экран живой, а текст не набирается. В логе
при этом всё честно:

```
get_selected_transport: Both endpoint transports are ready. Using 0
```

`Using 0` — это USB. Клавиши на слое 2 переключают выход вручную: `&out OUT_USB`
и `&out OUT_BLE`, в правой колонке рядом с управлением BLE.

## Отладочная сборка

`sweep_dongle_debug` из `build.yaml` — та же прошивка со снипетом
`zmk-usb-logging`. Даёт **второй** порт CDC, на который сыплется лог ZMK;
первый остаётся под метрики мака.

```bash
ls /dev/cu.usbmodem*                       # портов будет два
cat /dev/cu.usbmodem<второй> | tee dongle.log
```

Что в нём читать:

| Строка | О чём |
|---|---|
| `le_param_updated: … interval 12 latency 0 timeout 400` | какие параметры соединения назначил хост |
| `split_central_connected` / `[SUBSCRIBED]` | половина подключилась к донглу |
| `[DEVICE]: …` | увиденное при скане объявление; **фильтр дубликатов включён**, каждый адрес логируется один раз, так что тишина в логе не означает, что скан не идёт |
| `Trigger key position state change for N` | нажатие доехало с половинки |
| `get_selected_transport` / `Endpoint changed` | куда уходят HID-отчёты |
| `Not sending, no active address for current profile` | активный BLE-профиль пуст, бонда в нём нет |

Проверить встречную сторону — дошло ли до мака — можно счётчиком системы, он
считает нажатия любого источника:

```swift
CGEventSource.counterForEventType(.combinedSessionState, eventType: .keyDown)
```

Пара «в логе отчёт ушёл» плюс «счётчик не сдвинулся» делит задачу пополам:
до этого места виноват донгл, после — мак.

## Какая плата есть какая

Все три платы — nice!nano v2, и в бутлоадере они неразличимы: том называется
`NICENANO` у любой. Отличать их можно только по серийному номеру USB, он же
уникальный идентификатор чипа и не меняется ни при перепрошивке, ни при входе
в бутлоадер.

| Серийник | Имя на USB | Плата |
|---|---|---|
| `0E45FB20FA090F7A` | `Sweep Dongle` | донгл |
| `84F4C5EE425E77D1` | `Cradio` | левая половина |
| `8A21548861988209` | нет имени | правая половина |

Имя на USB берётся из `CONFIG_ZMK_KEYBOARD_NAME`, а в шилде `cradio` оно
задано только для левой половины — правая его не объявляет, поэтому строки
продукта у неё нет вовсе. Заодно это отличает половины друг от друга без
серийников.

Посмотреть, что подключено:

```bash
ioreg -p IOUSB -w0 -l | grep -E '"USB Product Name"|"USB Serial Number"'
```

**Проверять серийник перед записью обязательно.** Прошивка донгла, залитая в
половину, делает её центральным устройством: она перестаёт подключаться к
донглу и при этом честно представляется как `Sweep Dongle` — то есть проверка
«появилось ли нужное имя после записи» такую ошибку не ловит. Именно так одна
половина и была потеряна на полдня.

## Распиновка

| Сигнал панели | Пин nice!nano | GPIO nRF52840 | Ряд |
|---|---|---|---|
| VCC | `VCC` (3.3 В) | — | правый |
| GND | `GND` | — | правый |
| SCL (SCK) | `D15` | P1.13 | правый |
| SDA (MOSI) | `D14` | P1.11 | правый |
| CS | `D2` | P0.17 | левый |
| D/C | `D3` | P0.20 | левый |
| RES | `D4` | P0.22 | левый |
| BUSY | `D5` | P0.24 | левый |

MISO не подключается — SSD1681 ничего не отдаёт.

Порядок пинов на гребёнке модуля WeAct сверять **по шелкографии**, а не по
позиции: у разных ревизий он отличается.

### Почему не штатный `pro_micro_spi`

Дефолтный `spi1_default` у nice!nano сажает MOSI на **P0.10**, а это NFC-вывод.
`CONFIG_NFCT_PINS_AS_GPIO` в дереве ZMK не включается нигде, поэтому P0.09 (`D10`)
и P0.10 (`D16`) как GPIO недоступны. В оверлее pinctrl переопределён: MOSI
уходит на P1.11, MISO не заявляется.

### Питание

Гребёнка `VCC` у nice!nano v2 запитана через ключ на P0.13 (узел `EXT_POWER`,
`zmk,ext-power-generic`). `CONFIG_ZMK_EXT_POWER` по умолчанию `y`, ключ
включается на старте с задержкой 50 мс — но если внешнее питание когда-нибудь
выключится, дисплей встанет. Глубокий сон на донгле отключён.

## Экран

Рисуется через штатный хук ZMK `zmk_display_status_screen()`
(`CONFIG_ZMK_DISPLAY_STATUS_SCREEN_CUSTOM`), код — в `dongle/src/screen.c`.

Отдельная политика обновления e-paper не понадобилась: `display_tick_cb` в ZMK
— это просто `lv_task_handler()`, а LVGL уходит во flush только по
инвалидации. То есть панель обновляется ровно тогда, когда меняется текст.
Отсюда два требования:

- `CONFIG_LV_Z_VDB_SIZE=100` — полноэкранный буфер (200×200×1 бит = 5000 байт).
  При меньшем LVGL сбрасывает кадр полосами, а `ssd16xx` делает refresh на
  каждый `display_write` — вместо одного обновления вышло бы несколько подряд;
- `set_text_if_changed()` в `screen.c` — `lv_label_set_text` инвалидирует
  область независимо от того, изменился текст или нет.

Весь текст на экране — ASCII: встроенные шрифты Montserrat кириллицы не
содержат.

## Kscan-заглушка

Клавиш нет, но ZMK требует `zmk,kscan`. `zmk,kscan-mock` не подошёл: без
свойства `events` он не компилируется (`DT_N_S_kscan_P_events_LEN`), а задержка
события в нём кодируется 15 битами — отложить дольше 32.7 с нельзя. Поэтому
обычный `zmk,kscan-gpio-direct` на один физически не разведённый вывод `D9`.

## Протокол от агента на маке

Строки, ключи в произвольном порядке, незнакомые игнорируются, отсутствующие
сохраняют прежнее значение:

```
layout=RU cpu=23 mem=61 disk=142 batt=87 chg=1
```

Разбор общий для обоих каналов (`dongle/src/host_proto.c`). Раз в 5 секунд —
чаще e-paper всё равно не перерисуется. Сервис `f1ef61b7-…`, характеристика
`a336bc14-…`, запись требует шифрования, то есть сопряжения.

## Темпы обновления экрана

Блоки обновляются раздельно, и это принципиально. `ssd16xx` пишет только во всю
ширину, поэтому Zephyr расширяет любую грязную область до полной ширины
(`lvgl_rounder_cb_mono`, `SCREEN_INFO_X_ALIGNMENT_WIDTH`) — обновляется
горизонтальная полоса. Отрисовка далёких блоков в одном проходе склеилась бы в
полосу почти во весь экран.

| Блок | Когда |
|---|---|
| Заряд трёх устройств | не чаще раза в 5 с |
| Ресурсы мака | поводом не являются вовсе, рисуются попутно со сдвигом 1.5 с |
| BT-профиль | не чаще раза в 2 с |
| Слой | после 5 с стабильности |

Отрисовка вынесена в отдельную очередь работ
(`CONFIG_ZMK_DISPLAY_WORK_QUEUE_DEDICATED`). По умолчанию ZMK крутит её в
системной очереди — той же, через которую идут события клавиш от половинок, — а
`ssd16xx` на каждом обновлении ждёт на пине BUSY сотни миллисекунд. Ввод из-за
этого вставал колом.

## Энергосбережение

Пять минут без нажатий — панель не трогается совсем. Глубокий сон намеренно
выключен: он гасит радио, а разбудить донгл нажатием на половинке можно только
по радио, своих кнопок у него нет.


## Сборка

Только через GitHub Actions: пуш в репозиторий запускает
`build-user-config@v0.3`, готовые `.uf2` лежат в артефактах сборки.

```bash
gh run download --name firmware
```

Локальная сборка в контейнере была, но от неё отказались: воркспейс west это
79 тысяч файлов на 2.2 ГБ, и в индексируемом Spotlight каталоге он вгоняет
macOS в многочасовую переиндексацию — до отъедания свопа и подтормаживания
ввода. Если понадобится вернуть, разворачивать воркспейс надо **вне**
`~/Documents`.
